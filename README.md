# Libre AI Capability Authorization

## Intended use

Provide a distinct technical home for explicit, bounded Biscuit permissions used by services. An authorization decision concerns whether a particular action is permitted under the applicable facts and policy; it is not a user login or a business approval by itself.

## Existing candidates and limits

Earlier sources contain token issuance, attenuation, verification, revocation and key-rotation components. Their historical qualification does not admit a new package or operational issuer in this destination. This documentary candidate provides no usable tokens, service keys or deployed permission service.

## Authority boundaries and proposed contracts

Authentication remains in the Auth responsibility associated with Missions. Session and organization membership are separate facts whose actual authority must be qualified. A permission request identifies its resource, action and authoritative context; a refusal remains explicit when required facts or authority are missing. Attenuation may restrict an existing mandate, not create a broader one. Canonical formats and policies retain their designated authorities.

## Activation criteria

Qualify the exact issuer/verifier and a real consumer with bounded policy evaluation. Test altered tokens, unsupported keys, expiry, revocation, attenuation and cross-organization denial using synthetic credentials first. Verify that authoritative request facts cannot be supplied by an untrusted token holder. Keep browser authentication material, service permission keys and final Git signing keys distinct.

Qualification follows the actual selected scope. A candidate module may be admitted independently with its own consumer and evidence; complete journey criteria apply to the corresponding product or integration. A pure core does not require a worker, database or relay integration that is outside its scope. Neither module admission nor this repository’s documentary existence requires a complete Missions journey.
